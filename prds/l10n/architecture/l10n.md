# Arquitetura — l10n da interface

- **PRD:** [`../prd.md`](../prd.md)
- **Regras:** [`.agents/rules.md`](../../../.agents/rules.md) §5.1
  (R18–R22), BR-085/BR-086
- **Data:** 2026-10-22

---

## 1. Camadas

```
domain::settings::ui_language           ← valor, validação, sanitização
        ↑
application::ui_language_migration      ← resolve uma vez (SettingsStore + LocaleSource)
        ↑
ports::locale_source                    ← contrato (locale do SO)
        ↑
adapters::system::env_locale_source     ← LC_ALL/LC_MESSAGES/LANG/LANGUAGE
        ↑
lib.rs (composition root)               ← injeta e roda no boot
```

O frontend não detecta idioma. Ele lê `Settings.ui_language`, aplica no store
global e reage ao evento `settings_changed`.

## 2. Modelo

- `Settings.ui_language: Option<String>`:
  - `None` = ainda não resolvido (instalação nova ou settings antigas);
  - `Some("pt" | "en")` = escolha persistida, imutável automaticamente.
- `Settings::validate` recusa valor fora de `pt`/`en`; `sanitized` limpa um
  valor inválido para `None` (o boot resolve de novo).
- `UiLanguageMigration` só grava quando o campo está ausente/inválido. `save`
  é idempotente e roda antes de qualquer janela carregar as settings.
- `ui_language_from_locale`: `pt`, `pt-BR`, `pt_BR.UTF-8`, `pt_PT@euro` → `pt`;
  qualquer outro locale/ausência → `en` (fallback neutro).

## 3. Frontend

### 3.1 Catálogo

- `src/core/l10n/locales/pt.ts` e `en.ts`: objetos planos
  `Record<TranslationKey, string>`.
- `TranslationKey = keyof typeof PT`; o TypeScript recusa chave inexistente.
- `translate(key, language, params)` interpola `{name}`; fallback
  `idioma ativo → pt → chave`.
- O teste `src/core/l10n/index.test.ts` exige o **mesmo conjunto de chaves** e
  os **mesmos placeholders** em pt/en.

### 3.2 Store e hook

- `store.ts`: idioma global por webview + `useSyncExternalStore`.
- `useSettings` alimenta o store em cada `reload` (boot e `settings_changed`);
  `useUiLanguage` no `App` garante o mesmo para janelas que não chamam
  `useSettings` diretamente.
- `useTranslation()` devolve `{ language, locale, t }`. O `locale` BCP-47 é
  usado em `Intl`/`toLocaleTimeString`.

### 3.3 Rótulos dinâmicos

Enums de domínio não sabem a chave de tradução. `src/core/l10n/labels.ts`
centraliza a ponte (`speakerLabelKey`, `channelLabelKey`, `recordingModeKey`,
`shortcutActionKey`, `panelTabKey`, `agentIconKey`, …) e formatadores que
dependem de idioma (`formatDurationText`, `mediaLabelText`). Componentes não
concatenam chaves.

### 3.4 O que **não** se traduz

Transcrições, respostas do LLM, nomes/descrições de agentes criados pelo
usuário, títulos de sessão e labels de janelas fornecidos pelo SO. Esses dados
passam direto; o card de agente, o histórico e as bolhas mostram o valor
original.

## 4. Regra de contribuição (R18–R22)

1. Copy nova: adicione a chave em **pt e en** e use `t("chave")`.
2. Atributos (`title`, `aria-label`, `placeholder`, `alt`) também são copy.
3. Nada de `if (language === …)` dentro do componente: use `t`/helper.
4. Tela nova entra com teste no idioma de origem; fluxo global testa a troca
   pt→en e o re-render.
5. Texto de dados do usuário/LLM **não** entra no catálogo.

## 5. Fluxo de primeira inicialização

1. `settings.load()` → `ui_language = None`.
2. `EnvLocaleSource` lê o locale (`LANG=pt_BR.UTF-8`, por exemplo).
3. `ui_language_from_locale` → `pt`.
4. `settings.save()` grava `ui_language = "pt"`.
5. Boots seguintes: `Some("pt")` → migração não faz nada, mesmo com
   `LANG=en_US`.

## 6. Limites conhecidos

- Strings de erro vindas do core (provider HTTP, ASR) continuam no idioma do
  core; a UI as exibe como dado. Traduzir erros por código é uma evolução
  futura (exigiria códigos tipados no IPC).
- Menu da bandeja e tooltips do SO não passam pelo catálogo do webview nesta
  entrega.
